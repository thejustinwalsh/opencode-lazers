# pmndrs/pine deep dive: what LAZERS should take

Clone: `research/pine/repo` (HEAD `18825e0`, v0.22.2). Pine paths are relative to the clone. LAZERS paths are relative to `/Users/tjw/Documents/ChatGPT/opencode-lazers`. OpenCode paths are relative to the local OpenCode checkout `/Users/tjw/Documents/ChatGPT/opencode-native-settlement/packages` (commit `22e48b1`, 2026-11-17). Nothing from the pine clone was run. Two read-only measurement scripts imported LAZERS schemas; they live in `research/measure/`.

Scope (per lead correction): every pine feature is judged on what it is worth to LAZERS. Context size is one axis among the others.

## The finding that changes the ranking

Pine is built on the pi SDK (package.json:4). Pi declares every tool on its own, so pine had to write its own tool families, schema repair and cache warming. **OpenCode V2 already ships native versions of three of pine's context techniques, and LAZERS already uses one of them.**

| Pine technique                                                  | OpenCode native equivalent                                                                                                                                         | LAZERS today                                                                                                                                                                 |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool families + `find_tools` (catalogue.ts:575-815)             | Code Mode: one `execute` declaration, a catalog capped at 2,000 tokens, `search()` for the rest (core/src/codemode/catalog.ts:46-48, 54-136; instructions.ts:8-16) | Every `lz-*` tool registers with `codemode: true` (src/tools.ts:91 and others); no `codemode:false` left (design/reviews/codemode-and-rendering-observations-20261105.md:17) |
| `fit()` repairs arguments that are close (catalogue.ts:489-535) | `ToolInputRepairPlugin`: turns text into JSON, numbers and booleans; drops extra keys and null placeholders (core/src/plugin/tool-input-repair.ts:8-17, 31-48)     | Inherited: it runs on every inner tool call                                                                                                                                  |
| Fills idle cache slots ahead of time (agents.ts:3806-3856)      | `WarmingPlugin`: keep-alive requests every 4 min for 30 min (core/src/plugin/warming.ts:14-18)                                                                     | Config only, not adopted                                                                                                                                                     |

So for LAZERS the leftover context work is about **how LAZERS feeds Code Mode**: whether tools are grouped into namespaces, how long their signatures are, what the error text says when a call fails, and how long the prompt is. It is not about building a catalogue. Pine is designed for **small local models behind llama.cpp, where reading the prompt is the cost** (agents.ts:85, catalogue.ts:3-5). LAZERS' Architect and workers run hosted models with prompt caching. There a stable 5k-token prefix costs about 10% of its list price on each request, so the savings below are real but second-order.

## Design sketches: top 5

Attribution: pine is MIT, "Copyright (c) 2026 Paul Henschel" (LICENSE:1-3). The snippets below paraphrase pine's mechanisms. If code is copied rather than re-derived, keep the MIT notice in the copied file or in a `THIRD_PARTY_NOTICES` entry.

### 1. Neutral git for runtime calls

Files: `src/runner/artifacts.ts` (`git`, `gitAsync`), `src/runner/change-identity.ts`, `src/runner/takeover.ts`, `src/submission.ts`, `src/project-key.ts`. Put the shared argv prefix in one helper (for example `src/runner/git-neutral.ts`). Interface: `gitAsync(dir, args)` prepends `await neutralArgs(dir)`, which is memoised per (common dir, config mtime).

Pine's core (worktrees.ts:69-79), paraphrased:

```ts
async function neutralArgs(cwd: string): Promise<string[]> {
  const out = await git(cwd, ["config", "--name-only", "--get-regexp", "^(filter|merge)\\."])
  const filters = new Set<string>(),
    drivers = new Set<string>()
  for (const l of out.split("\n")) {
    const f = /^filter\.(.+)\.[^.]+$/.exec(l)
    if (f) filters.add(f[1])
    const m = /^merge\.(.+)\.driver$/.exec(l)
    if (m) drivers.add(m[1])
  }
  return [
    "-c",
    "core.hooksPath=/dev/null",
    "-c",
    "core.fsmonitor=false",
    ...[...filters].flatMap((n) => [
      "-c",
      `filter.${n}.process=cat`,
      "-c",
      `filter.${n}.clean=cat`,
      "-c",
      `filter.${n}.smudge=cat`,
      "-c",
      `filter.${n}.required=false`,
    ]),
    ...[...drivers].flatMap((n) => ["-c", `merge.${n}.driver=false`]),
  ]
}
```

Keep `signingArguments` (artifacts.ts:206): signing stays as configured (AGENTS.md). A neutralised merge driver turns into a conflict, which is the right outcome: the runtime then records a conflict and does not run worker-controlled code.

### 2. Host baseline and mock provider

Files: new `test/host-baseline/` (one file per check, named like pine's `C6`), `test/support/mock-provider.ts`, and a provider entry that `src/verification/opencode/owned-launch.ts` writes into its owned config pointing at the mock. Script `bun run baseline` runs only when OpenCode is bumped. A table in `.agents/docs/opencode-api.md` maps each check to its mitigation.

Mock contract (mock.mjs:1-5), paraphrased:

```ts
// The last user message may carry <<MOCK {"steps":[...]}>>.
// step = { tools?: [{name, args}], text?, delayMs?, stall? }
// Step index = number of assistant messages after the directive message.
const dir = lastUserWith(/<<MOCK (.*)>>/, body.messages)
const step = dir ? dir.steps[assistantCountAfter(dir.at, body.messages)] : { text: echo(body) }
state.requests.push({ url, body }) // tests assert the prefix, the catalog and the tools
if (state.failNext.length) return reply(state.failNext.shift())
return step.tools ? streamToolCalls(step.tools) : streamText(step.text)
```

First checks: (a) does a `.opencode/` plugin written into a worker worktree load (#3); (b) is `location.reload` server-wide; (c) are repair-plugin rewrites visible in `execute.before`; (d) the size of the Code Mode catalog with `lz-*` registered, asserted from recorded requests (this turns the estimate in #6 into a number).

### 3. Full help on failure (and deleting the 1,200 cap)

Files: `src/tools.ts` (`result()` and every `catch` at about lines 105-114, 160, 194-200), `src/progress/schema.ts:5`, `src/progress/recorder.ts:2066`, `src/progress/projection.ts:354`. Interface: one `explain(toolName, schema, issues)` that renders `issues` plus a compact signature built from the Zod schema. It runs only on `status: "invalid"`. Aliases live next to each tool's schema as a `Record<string, string>` applied in `execute.before`, after OpenCode's repair.

Pine's core (catalogue.ts:740-743), paraphrased:

```ts
const said = textOf(outcome)
const wrongArgs = WRONG_ARGS.test(said) && !/not approved|refused|denied/i.test(said)
throw new Error(
  `${said}${wrongArgs ? `\n\nWhat ${name} takes, in full:\n${helpOf(tool, name)}` : ""}`,
)
```
