# Architect: API feasibility and definition audit

Checked 2026-10-31 against OpenCode 2.2.5, commit `9bbb8ce18c80f099e0e448775f59d965ead40a21`.

Current authority supersedes the historical restricted slice below: Architect
retains normal OpenCode tools, including Code Mode, research, shell, editing and
Git, under host/user/project permissions. It reviews and integrates results;
runtime owns task dispatch and state transitions. Web provider availability is
still a separate native configuration concern.

## Verdict

The proposed experience is feasible as one OpenCode plugin used from native Desktop. The API supplies the agent, tools, sessions, models, events, permissions, and prompt delivery primitives. LAZERS must implement task admission, dependency scheduling, acceptance, budgets, recovery, and orchestration commands. Source compatibility and the current packaged slice are validated; the complete experience is not implemented or proven in Desktop yet.

Subsequent [Desktop evaluation](spikes/006-architect-interview.md) verifies native agent selection, repository investigation, structured questions with continuation, schema-valid submission, and persisted task receipts through the ChatGPT subscription. The historical pending-trial entries below describe the initial audit. The evaluation separates structural validity from semantic quality: Luna plans omitted a real process-restart check, motivating a generic verification refinement. One fixture across models does not establish broad generalization or an optimal definition. No scheduler or retry feature was implemented in this evaluation.

An important correction to the earlier handoff: having no `AgentEditor.add` does **not** prevent creating an agent. In this pinned release, `update(id, callback)` initializes a missing agent. The [core implementation](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/agent.ts) and [public plugin adapter](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/plugin/host.ts) establish this, and the packed-plugin probe below confirms it. Keep this behavior under an upgrade compatibility check.

Resume logic must reconstruct work from persisted state after reload/restart. Native timed schedules enqueue prompts; they do not implement dependency scheduling.

| [SWE-agent](https://github.com/SWE-agent/SWE-agent), [SWE-bench](https://www.swebench.com/), [Terminal-Bench](https://www.tbench.ai/) | Evaluate artifacts and tool traces against fixed tasks. Additional primary guidance supports the authoring approach: [Anthropic context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) favors small, useful context without brittle prompt logic; [tool design](https://www.anthropic.com/research/writing-tools-for-agents) puts precise interfaces and useful errors in tools; [agent eval guidance](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) distinguishes traces from actual outcomes and calls for repeated trials. [OpenAI prompting guidance](https://developers.openai.com/api/docs/guides/latest-model) recommends removing repeated instructions and testing changes on representative work. These are authoring principles, not proof of this definition's performance.

## Definition and enforcement

`src/architect.md` is the packaged source of truth. `src/architect.ts` decodes it with the pinned native agent schema and registers a fresh copy on transform replay. A repository-local agent file is no longer required. Repository `opencode.json` only selects the default; installing the plugin elsewhere exposes Architect for selection without forcing it as the default.

The body fell from 529 words / 3,807 UTF-8 bytes to 138 words / 1,057 bytes. These are footprint measurements, not tokenizer counts or a quality score. The removed material repeated tool schemas, denied actions, numeric defaults, provider billing guidance, and unavailable future features. The retained guidance covers investigation, material questions, observable acceptance, proportional verification, schema-bound handoff, and truthful result reporting.

| Responsibility                                                          | Owner and mechanical check                                                                                                                                                                                  |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Role, ambiguity, useful evidence, sensible decomposition                | Agent definition; evaluate decisions on representative feature requests.                                                                                                                                    |
| Fields, identifiers, evidence references, explicit limits, valid status | Zod/tool validation and behavior tests. Schema validity alone cannot prove semantic completeness.                                                                                                           |
| Identity, session/repository/revision provenance, durable receipt       | Submission/storage code; tests include unborn Git and database reopening.                                                                                                                                   |
| Editing/shell/delegation authority                                      | Permission rules and native assertions, not a long prohibition list in the prompt.                                                                                                                          |
| Retry/repair counts, cost/routing policy, runtime acceptance            | Runtime policy as those increments are implemented. Existing prompt/tool advice is not enforcement.                                                                                                         |
| Specialized knowledge                                                   | A skill only when it adds non-obvious task knowledge; concise description, focused body, references/scripts loaded when needed. No new skill is needed for this simple role merely to duplicate its prompt. |

## Verification and remaining gates

`bun install --frozen-lockfile`, native formatting/lint/typechecking, and 16 behavior tests (75 assertions) pass. A new test checks missing-agent registration and isolation across transform replays; it does not grade exact prompt wording.

The tarball from `bun pm pack --ignore-scripts` was extracted outside this checkout and installed with production dependencies. It contains `src/architect.md`. A clean temporary Git project configured only that packed plugin plus the no-model [host probe](../../test/host-probe.ts), with **no agent file**. OpenCode 2.2.5 loaded the plugin as active through Portless at `https://lazers-package.localhost:1355`. The probe returned:

```json
{
  "agentPresent": true,
  "mode": "primary",
  "description": "Defines scoped tasks and acceptance evidence from repository findings",
  "tools": ["lz-submit-task", "lz-get-task", "lz-list-tasks"],
  "permissions": {
    "read": "allow",
    "glob": "allow",
    "grep": "allow",
    "question": "allow",
    "lz-submit-task": "allow",
    "edit": "deny",
    "shell": "deny",
    "subagent": "deny",
    "execute": "deny"

```

The probe creates/removes a temporary session, checks native permission evaluation, and makes no model calls. The initial probe fixture omitted required RPC `events: {}`; that fixture was corrected and is included in typechecking. The product plugin stayed active throughout.

Native Desktop was inspected and showed Architect in its dropdown, but its selected directory was `/`. That is not evidence of this checkout's submission behavior. No prompt was sent or provider call made. Complete these Desktop/model trials before calling the Architect effective:

| Trial                                                          | Evidence to grade                                                                                                                                                                                                                            |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Clear, scoped feature request                                  | Relevant repository reads; a valid task row and receipt; stated constraints preserved; acceptance demonstrates requested behavior; no unnecessary questions or implementation writes.                                                        |
| Materially ambiguous request                                   | Focused native question before any valid submission; use the answer in the eventual task.                                                                                                                                                    |
| Invalid submission feedback                                    | Specific tool errors; at most the configured correction; no invalid row. Deterministic layer is already covered by tests.                                                                                                                    |
| Retrieval after Desktop/host restart                           | Same UUID/specification; no duplicate submission. Database reopening already passes in tests.                                                                                                                                                |
| Request requiring unavailable current-web research or dispatch | Report the missing capability; do not fabricate research, work, or acceptance. Enable and verify those tools in their own increments.                                                                                                        |
| Definition comparison                                          | Run old/new definitions on the same model/reasoning setting, fixtures and starting context for multiple trials. Grade final rows/artifacts and decisions; record tokens, elapsed time, calls, repeated reads, questions, and estimated cost. |

Tool/state checks establish structure and enforcement. Semantic acceptance quality and the minimum useful prompt require observed model behavior; neither a word-count target nor a prose/regex test can establish them.
