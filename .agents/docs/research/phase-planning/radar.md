# Phase 1 Radar — draft for discussion

## Goal and visual hierarchy

Radar is a live operational map of LAZERS scheduler components, native sessions and agents, their actual model routes and states, and message/data flow, in Project or Session scope. Keep plan/task context visible so an operator can connect activity to work. Show the full available system with live operations visually primary; retain detail through selection and scrolling rather than discarding it. Use a narrow native side panel: visualization above a horizontal, pointer/keyboard-resizable divider, selected component/session/edge details below. Tasks and Trajectory establish the quiet surface, clear hierarchy and inspector. Use native host theme and fonts.

Proposed map: group stable scheduler/runtime components as the infrastructure spine; connect actual Architect and worker sessions, showing agent, exact observed provider/model/variant when available, and session state. Associate them with actual plan/task/attempt context. Compact node names and state are visible; full identity, timestamps, reasons, model provenance and related session/task links belong in the inspector. Project includes associated work across the project; Session limits associations to that session. Default to LAZERS-managed sessions; an explicit option includes other native sessions within the selected scope. Missing data remains explicitly unavailable.

## Node and edge semantics

- A component is a real LAZERS runtime responsibility, not an invented process. A session node identifies a real native session, carrying its agent and observed model route. A task/plan/attempt is a distinct record, not an agent or component. Component names and relationships must map to actual code and record producers.
- Edge kinds must say what they mean: dispatch/assignment, prompt or outcome delivery, observation/read, and task dependency are different relationships. Draw an observed message pulse only for an identified recorded event, on the correct edge and direction. An architectural connection can exist without claiming a transfer is happening. Dependency edges do not mean communication. Selecting an edge shows its kind, evidence and status.
- Keep states distinct: native busy/idle is session state; task runner state is task state; outcome persistence, native admission and consumption are separate facts. Live cues stop on stale/disconnected observations; show last observed time. Reduced-motion mode preserves static status. Selection, focus and status have non-color indicators, and an accessible ordered representation covers nodes and edges.

## Telemetry: available and needed

- Current `src/observability/contract.ts` already projects scoped plans, titles, task objectives/state/reasons, dependencies, recorded transitions, attempts and checks, plus observation boundaries and change events. It does **not** currently expose graph-ready native session/agent/model nodes, component activity, or typed message-flow edges.
- `src/runner/store.ts` persists attempt session/message identifiers, continuation/session/model data and outbox/delivery records. `src/runner/native.ts` reads native session identity, parent, agent, model, busy/idle timing and outcome through the pinned host; `src/observability/associations.ts` establishes scope associations. Trajectory can supply deeper selected-attempt detail. These sources require a bounded scoped projection; their presence does not mean every state or message is presently exposed or observed.
- Add explicit stable node/edge identities and provenance, nullable fields and timestamps, mapping recorded attempts to sessions and plan/task, and documented delivery stages. Obtain actual provider/model/variant from the relevant native observation/record, distinguishing configured route from observed use and preserving unknown or changed models; do not claim a configured model was used without evidence. Determine which native events support active agent state and individual message edges; implement missing instrumentation if needed, rather than animating imagined traffic. Preserve privacy and scope boundaries on message metadata.

## SVG and layout guidance from gh-wat-dis

The referenced [gh-wat-dis](https://github.com/thejustinwalsh/gh-wat-dis) at `d61fbf53c9d5d8a8790bf0cbe8e62140c998eea9` provides actual prior art. Its [layout](https://github.com/thejustinwalsh/gh-wat-dis/blob/d61fbf53c9d5d8a8790bf0cbe8e62140c998eea9/src/diagram/layout.ts) uses bundled elkjs, measured text and badges, group-title reserved space, orthogonal routes, collision/crossing helpers, and compact detail for larger graphs. Its [SVG renderer](https://github.com/thejustinwalsh/gh-wat-dis/blob/d61fbf53c9d5d8a8790bf0cbe8e62140c998eea9/src/diagram/svg.ts) draws rounded orthogonal edges, arrowheads, labels, grouped nodes and textual descriptions; [dynamic example](https://github.com/thejustinwalsh/gh-wat-dis/blob/d61fbf53c9d5d8a8790bf0cbe8e62140c998eea9/examples/diagrams/dynamic.json) identifies participants and ordered relationships. It renders authored static diagrams for GitHub; the inspected implementation does not establish live updating, incremental stability, or interactive panel support.

Adapt the ideas, not its fixed GitHub page dimensions or estimated Helvetica metrics: measure using actual host fonts; give ELK node/group/label space, render SVG geometry and native interactive controls, wrap long names and scroll at readable size. Use stable IDs and deterministic order. Cache geometry by scope/topology; status refresh should not relayout. On topology changes seed prior positions and evaluate ELK's interactive/model-order strategies, preserving selection and viewport; avoid stale asynchronous results. A readable accessible list is the fallback if layout is unavailable. Use only the quiet activity animation the evidence supports.

## Proposed tasks

1. **Operational projection.** Done: scoped components, actual sessions/agents/models, task context and typed, evidence-linked relationships update correctly; reconnect and stale behavior remain honest. Sources: observability, runner/native/store, pinned V2 API. Pitfalls: configured vs used model, admission vs consumption, and session state vs task state.
2. **Radar view.** Done: SVG/elkjs map makes live system activity and selected detail readable in narrow Desktop, with stable layout across status updates, host theme/fonts, keyboard selection, independent scrolling, horizontal split and reduced motion. Exercise a real active multi-agent run, scope switch, stale state and host font/theme changes. Pitfall: clutter from showing all details inline; show all real entities while progressively revealing their details.
3. **Task investigation path.** Done: make history discoverable and open a selected completed task in Trajectory with identity preserved. This can be independently scoped from Radar. Continue the production audit's lifecycle, privacy, renderer freeze and incremental trajectory work in their existing boundaries.
