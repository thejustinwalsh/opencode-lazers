# Radar first native capture — design review

**Not ready for visual acceptance.** The captured initial map shows only a few dotted line fragments in a large empty field: no visible scheduler, session, model, task or message identity. The operator cannot orient or select work. Driver reports 115 node elements across a 10,155 × 8,599 SVG for 35 managed sessions; the screenshot itself shows only a small top-left fragment. `map-view.tsx` renders the SVG at its full computed width/height and `.lazers-radar-map-frame` is max-content; `layout-graph.ts` lays all groups and cross-group relationships in one RIGHT-directed compound ELK graph. This makes the initial viewport's useful content depend on where ELK places it. A fit-to-window scale would make the existing 10–12px labels unreadable and is not a fix.

**Proportional correction:** keep the full data/model available, but create a compact initial operational overview derived from it. Place the actual scheduler/runtime spine at the top of a vertical narrow layout; show the current Architect and active/relevant worker sessions nearest it, each with agent, native state, observed model/effort and concise task context when present. Use meaningful group summaries for the other recorded sessions, plans, routes and tools, with count and explicit expand/drilldown to individual records and relations. Show all records through those groups and the accessible list rather than silently dropping history. If activity cannot be verified, show last-known or unavailable instead of inventing active sessions. Keep actual type/identity and route provenance intact.

Lay out the overview with ELK using a narrow target and measured native font dimensions, bounded-size node labels, and orthogonal lines; place recorded message/delivery relations on the relevant visible nodes, with a brief pulse only for fresh evidence. Place detailed historical/cross-group edges in the expanded view or selected inspector, not as an all-to-all labeled initial topology. Keep compact controls/status above and retain the horizontal, independently scrollable inspector below. Session status/model belongs directly on the session node, not on a distant route node that requires traversing the giant canvas. The selection inspector should lead with human name/status and related task, with IDs and evidence lower down.

Make the initial origin intentionally land on the overview's meaningful content at 330–450 CSS px; preserve user viewport and selection on subsequent refresh and avoid reshuffling for status changes. Keep text at host size and scroll vertically; horizontal scrolling is a secondary path for real expanded complexity. Compress the three lines of technical freshness/coverage text into a compact truthful status with expandable coverage detail, retaining a clear stale/gap signal. The Tasks and Trajectory references show a readable focal area above the divider with selected detail below, unlike this capture's mostly empty visual field.

**Verification target:** recapture a connected multi-session overview at narrow width showing the scheduler, at least one real session and its model/effort or explicit unavailable state, task context and a readable evidenced connection without first scrolling a huge canvas. Check a group expansion and selection below, then confirm refresh maintains position; show a real event pulse only when the native feed supports it. This is a correction plan, not native acceptance.

**Packaging sanity check:** the narrow diff bundles the worker, injects its source and starts a `worker_threads` worker with `eval`, removing the `__dirname` dependency; the new test exercises a filename-free evaluator and real worker with a simple graph. Driver independently reports Desktop main and ELK now run. I did not run the build or test, and the test recreates the bundle using Bun rather than exercising the actual Vite output, so it does not alone prove the full packaging path. The visual scale problem is separate from that packaging fix.
