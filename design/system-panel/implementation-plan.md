# System panel: design and implementation plan

2026-10-31 · Approved design guidance for the optional System panel. The runner machine and durable runtime are available on main; this document describes the remaining scoped read projection and panel work. The panel is not implemented by this document.

## Decision and visual contract

System is an optional, closable native side panel for observing one real run. **Flow means the runner's live state machine**, not a task-dependency graph. The approved Flow image shows task dependency nodes, so it is a visual-family reference only: redraw and validate its semantics before implementation. Never rename task nodes as states. Dependencies are a separate domain and may appear as recorded wait causes or in a separately specified view, not as state transitions.

These are image-pixel proportions, not CSS pixel prescriptions. In Desktop use the Tasks panel's host typography, semantic theme tokens and native controls; the image's typography and colors are illustrative. Favor approximately 12–20 CSS px panel insets, a 4 px spacing rhythm, subtle borders and sparse semantic status accents, adjusted to host sizing and actual width. Preserve readable text rather than scaling the image down. Selection, status, and keyboard focus must remain distinct without relying on color. No dashboard tiles or decorative graph activity.

Component map: existing `Panel`/`MenuItem`/`Command`, `usePanel`, native `ctx.ui` controls and reactive appearance → System shell with scope and Flow/Timeline switch → vertically stacked scrollable visualization, full-width horizontal keyboard/pointer resizable separator, and shared selected-item detail. Reuse the Tasks split, selection, keyed scope, cancellation and session-store patterns where appropriate; extract common pieces only when warranted. Never create a right-hand inspector, including at wide widths. Preserve split and each pane's scroll and selection by server/project/session/scope; clear or explicitly indicate an unavailable selection when its identity no longer belongs to the scope. Long labels wrap; graph and timeline may scroll within their own pane rather than clip or shrink type.

## Flow semantics

Select a run/attempt explicitly where more than one exists. Show a compact top-to-bottom statechart for **that runtime machine definition and snapshot**: nodes are actual machine states (including explicit compound/parallel regions only when the definition supplies them); directed edges are actual defined transitions with event labels. Active state(s) get a persistent outline/icon and text; inactive states are subdued. Distinguish a defined but untraversed transition from a recorded traversed transition using line style and accessible label. Show a transition as observed only when its durable record identifies it; an active snapshot alone does not prove the path taken. Indicate initial/final states only when the machine defines them. Do not imply the whole graph is the execution history, that multiple active states are parallel unless the machine says so, or that an unobserved possible edge occurred.

Select a state to inspect its active status, recorded entry/exit and current wait/failure reason with causal evidence, when available; select a recorded transition to inspect event, time, source/target and associated attempt/evidence. Unknown data is labeled unavailable, not inferred. Architect appears as an explicitly recorded decision boundary or delivery/decision annotation linked to the relevant transition or wait, not a scheduler state invented for visual balance. Show delivery and decision status only from records. The lower detail is shared with Timeline and has task/attempt identity, recorded reason, next responsible actor when known, outcome persistence/delivery, and collapsed attempt details/activity. State/transition selection and timeline span selection resolve to their recorded entity, not an invented common identity.

Use stable deterministic layout keyed by definition version and state IDs; preserve node position across snapshot updates. Keep a narrow single-column spine with compact side branches for actual alternatives; scroll horizontally only when a real hierarchy/parallel region requires it. Avoid edge crossings where possible and offer a text/keyboard navigable ordered representation of states and transitions with equivalent information. Buttons/controls expose selection and focus; announce meaningful changes without continuous live-region chatter. Respect reduced motion: state changes remain legible without animated movement. Do not rearrange the graph on every event.

## Timeline semantics

Use one observed time axis and task/attempt lanes. Draw execution and verification as separate spans from recorded start/end times; an open span ends at the observed current time only while connected and confirmed active. A stale snapshot freezes at its last known timestamp. Show waits, failures, delivery and Architect decisions only when recorded, with distinct labels/line styles as well as color. Multiple attempts remain separate and traceable. No percent progress, predicted completion, synthetic history or placeholder production telemetry. Handle equal/missing/out-of-order timestamps honestly; the ordered event sequence is authoritative for causality, while timestamps locate observed spans. A selected span uses the same lower detail and source identity as Flow. Empty, unavailable, loading, stale and error states explain what is known.

## Data and implementation boundary

Verified here: `package.json` pins OpenCode/plugin 2.2.5, Solid and XState 5. `src/runner/machine.ts` defines the authoritative task machine; `src/runner/store.ts` persists plan/node snapshots and ordered transitions; `src/runner/runtime.ts` drives the durable lifecycle and runtime and adapter tests cover recovery and command behavior. Existing `src/tasks/contract.ts` exposes typed query/get and a project/version `changed` event for task records. `src/tasks/panel-state.ts` cancels obsolete requests, keys session/project scope, polls and refreshes after invalidation; `src/tasks/rpc.ts` publishes a durable SQLite watermark. These are integration patterns for the remaining projection, not a reason to create a second GUI runtime. Task submission still preserves immutable revision 1 with status `submitted`; execution state and outcomes are recorded by the runner. The API reference documents experimental Desktop GUI registry, Solid setup and typed RPC; `src/tasks/panel.tsx` demonstrates the actual panel wiring, canonical project resolution, session-scoped store, and host appearance usage.

The GUI consumes a versioned serializable topology and persisted state/transition read projection from the authoritative server runtime. Never start a second runtime actor or replay side effects in the GUI; historical selection projects records and never sends historical events to a live actor. Do not infer that transitions are enabled from guard labels without the applicable event and context. Never create a second authoritative frontend FSM. For a small, fixed real machine, prefer a lightweight deterministic SVG/DOM projection with accessible HTML controls, using definition IDs and stable layout metadata; evaluate a dedicated layout library only if actual hierarchy, edge routing or scale justifies its cost, Solid compatibility and accessible output. Layout is presentation metadata and cannot change runtime semantics. No specific library API is assumed.

The remaining scoped observation projection is task `efd8459f-1dbe-4472-968b-f26f59504291` (plan `b50a1a71-1a54-4d89-8ef2-0644bcccc327`); its implementation and verification are pending. It must expose canonical project and routed session/run associations, including explicit plan/worker links, while preserving project and session scope. The projection must include machine definition/version, run/task/attempt identifiers and revision, snapshot active states, ordered durable transition/outcome/decision records, reason and evidence references, timestamps, sequence/watermark, and availability/retention. Define a consistent snapshot plus cursor/replay boundary so updates during initial read are neither lost nor duplicated; events must be ordered and idempotently consumed, with gap detection, reconnect and full resnapshot if retention or version prevents replay. Persist outcomes before notification; show persistence and delivery as distinct facts. A disconnected, out-of-date, or failed resync view must identify last observation time and never present last-known state as live. Restart, missed events, duplicate events, changed definition and session switching need specified recovery tests. Radar/Flow UI remains unimplemented until this projection is available.

## Small increments and acceptance evidence

Each increment is independently specified by Desktop Architect and scoped to runtime capability actually available; this sequence is design guidance, not a mandate to build a complete scheduler before useful observation.

1. Complete the scoped observation projection task against the existing durable runner machine, snapshots and transitions. Verify association-aware reads, state, ordered events and restart recovery against a real run.
2. Build a read-only Flow for that real lifecycle. Verify active state, recorded transition selection, gap/reconnect and stale behavior; show honest empty/unavailable states. No mock production data.
3. Add Timeline when actual attempt and verification timestamps exist; verify overlapping attempts, open/closed spans and selected evidence against records. Add waits and decision/delivery annotations only as their durable contracts arrive.
4. Expand to multiple runs, real parallel regions, decision/recovery paths and larger graphs as supported and independently verified; preserve old attempt history and scope continuity.

For each visible slice capture the connected OpenCode Desktop panel alongside the relevant reference at comparable panel width and theme, with genuine recorded data and separately identified fixtures for difficult states. Capture narrow side-panel widths and horizontal split before/after pointer and keyboard resizing; exercise independent scrolling, long labels, empty/loading/error/stale/reconnect, session/project switches and reopen/restart. Compare hierarchy and spacing, not fabricated chart contents. Repeat in host light/dark themes and with changed UI/mono fonts; verify focus, keyboard access, screen-reader equivalents, reduced motion and no clipped controls. Record host/plugin versions, data provenance, screenshot pairs, observed behavior, discrepancies and deliberate semantic departures. A visual fixture, a green typecheck, or an image alone does not establish a connected live feature.
