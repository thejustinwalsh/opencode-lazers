The later spike is a different workload from the earlier idle service samples. Root's OS-only window at 1793839542408–1793839554446 measured service PID 95968 at 103.92%, renderer 54076 at 29.41%, and GPU process 54072 at 1.99%, with no diagnostic, build, test or model traffic from Root. GPU process CPU is not GPU utilization. Temporary profiler removal preceding this window does not establish causation.

The actual bounded JSC capture `/private/tmp/lazers-service-spike-20261104.json` covers 1793839736624–1793839746669, 10045 ms, 740 samples, with no competing Root traffic. Counted once per stack, snapshot handler appears in 152 samples, database-event listener in 81, source stamp in 72, trajectory status in 72 and projection loading in 60; these overlap and must not be added. This is actual history projection/invalidation work, not evidence that privacy regex primitives alone caused the spike. Root removed the temporary diagnostic again in canonical 383e6ed; the capture remains outside the repository.

Read-only counters at 1793839812584 found the latest 25 transitions were `ARCHITECT_RENEWAL_RECOVERY_FAILED`, every approximately 5–8 seconds, while worker progress had not changed since the earlier provider quota failure. Renewal `e7c359a6-7758-4336-85d1-6d74dbb29c74` started at 1793839177122 and remained `creating` with `Session.NotFoundError`. Its start is approximately the configured 30-minute idle threshold after the quota stop, and after the earlier post-repair service profile. The transition writes invalidate observing panels, explaining the previously unexpected snapshot/status workload. Source scanning before each failed successor lookup adds work to each retry.

The pinned 2.2.5 host directly delegates `ctx.session.get` to core `Session.get`; its error is tagged `Session.NotFoundError`. The HTTP protocol instead declares `SessionNotFoundError`. LAZERS handled only the latter, so an expected absent successor raised an exception before native creation. Verified primary sources at the pinned commit:

- [Host delegation](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/plugin/host.ts)
- [Core error definition](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/session/error.ts)
- [Protocol error definition](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/protocol/src/errors.ts)

The repair recognizes both exact missing-session tags only when the error names the requested session. Transport/authentication failures and different session IDs still throw; absence contradicted by native active/pending work still throws. This allows the existing renewal state machine to proceed normally on its existing authorized route; it does not switch providers, retry dirty workers, or alter inference settings.

A separate runtime repair performs a lightweight successor availability/identity preflight before the full history sweep. It preserves the existing fresh lookup after that sweep and all complete sweeps before creation/ownership transfer. No cached proof, truncation, backoff or retry budget is introduced. Repeated failures still retry, but an identical durable recovery issue (renewal ID, state and error, its entire payload) does not append another transition. A changed failure or recurrence after a different failure remains recorded. General renewalIssue events are unchanged.

Validation: 31 scoped native/renewal/archival/cancellation/race tests, 557 assertions pass (6.74 seconds); Bun check 350 files, four-file lint and format pass. New tests cover both pinned error shapes, wrong IDs, transport/auth errors, active-work contradiction, repeated unavailable successor lookup with zero history pages, successful later recovery with full sweeps and original worker attempt preserved, and identical/changed/recurrent failure recording while cancellation completes. Live post-activation performance remains to be measured; this report does not claim the CPU spike is resolved merely from source tests.


Live follow-up after the first activation exposed a second absent-session boundary: `workerObservation` queried the nonexistent successor's inbox after the core get returned null. The real public inbox endpoint also rejects with a same-ID `SessionNotFoundError`; the initial test stub incorrectly returned an empty list. The follow-up accepts that exact protocol error only in the already-confirmed-absent branch. Present-worker inbox errors, different IDs and other failures still throw; native active inventory is still required, and a successful nonempty inbox still contradicts absence. Concurrent creation remains covered by the later fresh session lookup and existing identity/readback checks. The complete native suite passes 33 tests/164 assertions, plus check348/lint2/format. Primary inbox mapping: [pinned session handler](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/server/src/handlers/session.ts) and [missing-session mapper](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/server/src/handlers/session-error.ts). This is a tested follow-up, not yet proof of a settled live CPU result.

## Settled outbox amplification and scoped repair

Source unreferenced counts reached zero at 1793841260998. Root's clean OS-only window 1793841295005–1793841307038 (12.033 s, same PIDs, active inventory empty, six flags true/demand false, no competing traffic) still measured service **73.05%**, renderer **0.42%**, GPU process **0%**. Reference drain therefore did not explain the remaining service load away.

The next bounded capture `/private/tmp/lazers-service-post-renewal-settled-20261104.json` covers 1793841473118–1793841483187 (10069 ms, 2517 samples). Top stacks include 274 stringify samples in native HTTP, 208 SQL values and 204 SQL parse samples under native HTTP, and 184 client response JSON parse samples. Async stack separation prevents assigning every native HTTP sample to one caller. The directly attributed delivery supersession `findLast` callback contributes 100 JSON parse samples. Source and the reproduced call count establish amplification: `deliverCurrent` reads the same native session for every admitted notice before returning without action; even a lightweight native session observation fetches the full inbox and execution/approval inventories. With 234 admitted rows this performs 234 same-owner native observations each pass. A reference/handoff row also searched the entire remaining delivery list even though its supersession predicate always returned false.

The focused repair skips that impossible supersession search and shares one fresh target validity observation only for already-admitted same-owner no-op rows within one delivery group. Durable ownership is rechecked after awaited native observation and for each row. No observation survives a pass or any path that may admit, cancel, retarget or otherwise mutate delivery. Invalid/unavailable targets and ownership changes retain the existing recovery paths. No notice, inbox entry, receipt, model route, source journal or acceptance state is removed or marked consumed by this optimization.

Regression with the actual backlog size reproduced **234 native target reads before, one after**, with identical durable outbox rows and no native writes. It verifies a fresh observation next tick, failure propagation, a fresh observation after an intervening admission, and current-owner revalidation across an await. Existing archival, consumption/cancellation races, uncertain admission, supersession and renewal tests remain green: 31 tests/518 assertions, 9.27 s; check348/lint2/format pass. An expanded test exposed a fixture mismatch introduced by our earlier blocked-context preflight: the succeeded-detail cancellation race supplied unknown background and thus never reached its intended detail read. The failure was reproduced with the unmodified pre-outbox runtime. Its succeeded fixture now supplies the valid zero-background prerequisite; the original cancellation race assertions and interrupted/missing unknown-background cases remain.

## LZ28/LZ30 context-contract recommendation (not implemented)

Read-only review of original LZ28 task `239f45a9-3247-4cba-b339-19c8267d0800` confirms the explicit small-handoff/live-task-state constraint and native wake-context measurement gate. Final live counts distinguish **234 admitted outbox rows = one handoff plus 233 source-reference notices**. Root measured the first handoff at 1793841670182 as 9003 text characters/9019 UTF-8 bytes, and the final source-reference inbox at 1793841673910 as 233 entries/651171 text characters. No additional model turns followed the initial quota-failed wake; billable tokens remain unknown. Reference-only history pushed in hundreds of separate notices still violates the fresh-context goal even without raw transcript replay.

Recommended repair belongs to the existing LZ28/LZ30 lifecycle contract, not a duplicate task: retain the complete predecessor journal/history, give the successor one compact source pointer/summary explicitly distinguishing unreviewed/unknown coverage, and expose source journal records progressively through the existing plan-inspection interface. Replace historical per-ID push batches with compact coalesced source-change notifications; preserve pending/steering input blockers, result revisions and separate actionable worker outcomes. Inspection currently has no dedicated source journal view, so merely suppressing all notices would be incomplete. Coalescing must preserve native in-flight/admitted identity and receipt rules; current `deliver` deliberately exempts all source-reference notices from supersession. Already-admitted notices must not be silently rewritten or deleted. This recommendation makes no retrospective checkpoint/consumption assertion and introduces no arbitrary context cap or model-budget setting. Its implementation and any existing-inbox recovery need the coordinated lifecycle plan, separate from the measured no-op delivery optimization.
