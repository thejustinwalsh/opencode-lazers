# Architect renewal failure caused the later idle CPU spike

The later spike is a different workload from the earlier idle service samples. Root's OS-only window at 1793839542408–1793839554446 measured service PID 95968 at 103.92%, renderer 54076 at 29.41%, and GPU process 54072 at 1.99%, with no diagnostic, build, test or model traffic from Root. GPU process CPU is not GPU utilization. Temporary profiler removal preceding this window does not establish causation.

The actual bounded JSC capture `/private/tmp/lazers-service-spike-20261104.json` covers 1793839736624–1793839746669, 10045 ms, 740 samples, with no competing Root traffic. Counted once per stack, snapshot handler appears in 152 samples, database-event listener in 81, source stamp in 72, trajectory status in 72 and projection loading in 60; these overlap and must not be added. This is actual history projection/invalidation work, not evidence that privacy regex primitives alone caused the spike. Root removed the temporary diagnostic again in canonical 383e6ed; the capture remains outside the repository.

Read-only counters at 1793839812584 found the latest 25 transitions were `ARCHITECT_RENEWAL_RECOVERY_FAILED`, every approximately 5–8 seconds, while worker progress had not changed since the earlier provider quota failure. Renewal `e7c359a6-7758-4336-85d1-6d74dbb29c74` started at 1793839177122 and remained `creating` with `Session.NotFoundError`. Its start is approximately the configured 30-minute idle threshold after the quota stop, and after the earlier post-repair service profile. The transition writes invalidate observing panels, explaining the previously unexpected snapshot/status workload. Source scanning before each failed successor lookup adds work to each retry.

The pinned 2.2.5 host directly delegates `ctx.session.get` to core `Session.get`; its error is tagged `Session.NotFoundError`. The HTTP protocol instead declares `SessionNotFoundError`. LAZERS handled only the latter, so an expected absent successor raised an exception before native creation. Verified primary sources at the pinned commit:

- [Host delegation](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/plugin/host.ts)
- [Core error definition](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/session/error.ts)
- [Protocol error definition](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/protocol/src/errors.ts)

The repair recognizes both exact missing-session tags only when the error names the requested session. Transport/authentication failures and different session IDs still throw; absence contradicted by native active/pending work still throws. This allows the existing renewal state machine to proceed normally on its existing authorized route; it does not switch providers, retry dirty workers, or alter inference settings.

A separate runtime repair performs a lightweight successor availability/identity preflight before the full history sweep. It preserves the existing fresh lookup after that sweep and all complete sweeps before creation/ownership transfer. No cached proof, truncation, backoff or retry budget is introduced. Repeated failures still retry, but an identical durable recovery issue (renewal ID, state and error, its entire payload) does not append another transition. A changed failure or recurrence after a different failure remains recorded. General renewalIssue events are unchanged.

Validation: 31 scoped native/renewal/archival/cancellation/race tests, 557 assertions pass (6.74 seconds); Bun check 350 files, four-file lint and format pass. New tests cover both pinned error shapes, wrong IDs, transport/auth errors, active-work contradiction, repeated unavailable successor lookup with zero history pages, successful later recovery with full sweeps and original worker attempt preserved, and identical/changed/recurrent failure recording while cancellation completes. Live post-activation performance remains to be measured; this report does not claim the CPU spike is resolved merely from source tests.
