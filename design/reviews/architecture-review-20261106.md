# LAZERS architecture review — 6 November 2026

**Conclusion:** the core authority split is sound: OpenCode owns native execution, LAZERS owns durable orchestration, and Desktop owns presentation/local inference. The important deviations are competing publication and ownership rules, a long-running activity inside the reconciliation drain, and verification failures routed to repair without distinguishing inherited baseline defects. No P0 is established. Address the four P1 boundaries below through existing work where applicable; preserve original tasks, attempts, native sessions, artifacts and usage.

This is a current-source, system-boundary audit, not a line-by-line correctness proof. It traces bootstrap, native adapters, commands, scheduler, persistence, progress/recovery, model/pricing, context, panels, GPU/audio and verification. It does not change runtime code, production SQLite, inference settings or workers, and sends no model prompts. The canonical checkout and active native candidates can differ. In particular, LZ-163's delivered correction is pending its real combined acceptance/integration; LZ-168 has delivered its repair; LZ-169 and LZ-155 remain the existing UI/trajectory lanes. Delivery is distinct from integration and native visual acceptance. Their work is not declared absent or replaced here.

## P1 findings, ordered by user impact

### A1 — Observability still multiplies publication across locations

**Proven current defect; existing LZ-129 boundary.** Each registration constructs its own `ObservationChangeTracker`, publishes its own `changed` events, subscribes to the same database changes, and starts its own native event stream: `src/observability/rpc.ts:95`, `:231`, `:274`, `:286`. The per-instance sequence/native/live-session state is visible at `src/observability/changes.ts:104`. Shared association reads reduce SQL work but do not share publication.

The [native amplification observation](renderer-event-amplification-20261106.md) recorded 368 observability events in three seconds, 69 distinct complete change identities, with identical records repeated 14 times across 14 locations; two other trackers had different baselines. This directly proves duplicate publication. It does not establish the cause of every renderer freeze or mean all 368 events were duplicates. Tasks publication has already been corrected and observed at one event per version; do not reopen that solved publisher (`src/database-events.ts:95`, `src/tasks/rpc.ts:302`).

**Impact:** extra event transport, invalidation, timers and panel refresh work grow with loaded worktrees. This is consequential during parallel execution and navigation.

**Small task:** complete the existing observability coordinator work: one canonical project/source publisher with explicitly scoped per-reader session/live-event queues. Keep reconnect/gap identity, permissions, subscriber disposal and distinct project isolation. Do not deduplicate by bare tracker sequence: different trackers can have the same sequence for different observations. Acceptance: many location registrations produce one canonical event identity per source change; each subscriber still receives its own relevant scope/live changes; reload/failure/disposal cannot lose catch-up. Reobserve actual event counts and responsive navigation. Do not promise a total CPU fix from this change alone.

### A2 — Verification occupies the single project reconciliation drain

**Proven control-flow coupling; production latency magnitude unmeasured.** The coordinator elects one non-overlapping project drain (`src/runner/scheduler-coordinator.ts:128`). `TaskRuntime.tick()` awaits each plan's `step()` before reaching delivery (`src/runner/runtime.ts:5830`, `:5861`, `:5865`). A step awaits active attempts; ordinary verification then awaits `runCheck` (`:5935`, `:7562`), which waits for subprocess completion/output (`src/runner/artifacts.ts:433`). Ordinary verification does not pass an abort signal to `runCheck`; retained verification has a separate abort/controller protocol. Checks have positive caller-specified timeouts, not a product-imposed maximum (`src/task.ts:82`).

The adjacent [isolated flow probes](architecture-flow-probes-20261106.ts) run the real tick and subprocess runner with fake store/native boundaries. During a real `sleep 0.35` check, only the first plan had stepped at 51 ms; a second tick returned without stepping another plan or delivering outcomes; both occurred after 421 ms. This is a bounded flow reproduction, not a production cancellation walkthrough. A native worker can keep executing while the drain waits. Cancellation intent can be recorded by a concurrent command, but normal cancellation reconciliation and unrelated delivery wait for the drain; the current check is not interrupted through this path.

**Impact:** one slow check delays unrelated same-project dispatch, delivery, cancellation reconciliation and explicit Start completion. A shared scheduler timer removes duplicate wakeups but cannot fix work awaited inside a drain.

**Small task:** retain the existing journaled check identity/receipts and run ordinary checks as tracked asynchronous activities. A tick should start/reconcile an activity and yield; completion requests a tick. Bind cancellation/disposal to that exact activity and keep uncertain process outcomes explicit. Do not add a daemon or replay uncertain checks. Acceptance: a deliberately blocked real check coexists with dispatch/delivery/cancellation of another eligible plan; no check overlap, stale acceptance, orphan subprocess or lost final receipt across restart. Preserve meaningful artifact/environment/input validation.

### A3 — Launch parent competes with current plan authority during retained repair

**Proven canonical-source defect; use existing LZ-163 correction.** `retainedRepairWorkerProblem` requires `worker.parentID === plan.owner` (`src/runner/runtime.ts:1004`). Native parent is immutable launch history; plan ownership can change through supported renewal/reassignment. Terminal continuation already checks current caller/owner and exact attempt/input/route without requiring that parent equality (`src/runner/interrupted-continuation.ts:92`, `:160`). These are competing rules for the same ownership concept.

The [actual LZ-129 sequence](ownership163-live-sequence-review-20261106.md) contains three `OWNER_CONTINUED` transitions followed by `OWNER_REASSIGNED`; no direct original-parent-to-current-owner edge exists. The isolated predicate probe changes only plan owner: launch owner is allowed; transferred owner is rejected as changed worker identity. Root reports LZ-163's delivered candidate passes 377 tests/5,656 assertions, but canonical integration and its real retained-worker acceptance remain separate.

**Impact:** valid original workers cannot receive authorized repairs after owner renewal, encouraging unnecessary replacement work or manual rescue.

**Small task:** finish and verify LZ-163 against the original worker and full recorded transfer sequence. Use current durable plan authority/control epoch, exact attempt/project/workspace/route/native input and effect receipts. Native parent stays historical evidence; do not add archive prerequisites, ancestor scanning, a second lineage service or replacement attempts. Acceptance includes multi-hop renewal then reassignment, unauthorized/stale owners rejected, and the same original worker successfully admitted once.

**Observed failure-routing defect.** Read-only original check receipts show:

| LZ-163 / `0eeb5b3b…`    | `bun fmt --check && bun lint && bun check && git diff --check`                      | Only the same pricing report needs formatting                                                                     |

These compound receipts stopped at formatting; they do not themselves prove later checks ran. Separate worker checks are separate evidence. Original attempts became failed; repair attempts `fb309498…` and `130e1ffc…` were created. Root's native observation established that these were untouched inherited baseline files, canonical formatting had already been corrected, and stale worktree baselines plus LZ-163's active reservation prevented a straightforward cross-lane report fix. The extra attempt is measured overhead; a dollar or active-time cost is not established here.

Ordinary verification maps any failed receipt to `failAttempt` (`src/runner/runtime.ts:7596`); `failAttempt` turns a verifying node into `REPAIR` when the ordinary default permits it (`:10717`). There is no diagnostic distinction here between an introduced defect, inherited baseline failure or unavailable environment.

**Impact:** independent correct work incurs new inference, new attempts and scope decisions for an unrelated mechanical failure. The repair can itself be unable to edit the failing file.

**Small task:** run deterministic formatting through the already-authorized scope when appropriate, then classify quality failures before assigning unrelated edits. Reuse available baseline receipts; compare a failing baseline only when needed to distinguish inherited/environment failures from introduced defects. This is no blanket baseline gate: do not run the full suite twice per task or add a model call for classification. Inherited failures should produce an actionable hold. Preserve repository-wide final checks on the accepted combined artifact. Do not silently ignore failures, rewrite immutable specifications, or weaken acceptance. Acceptance: reproduce the two baseline failures; no replacement model attempt for unchanged unrelated formatting; introduced formatting regressions still fail; combined checks remain mandatory and evidence stays revision-bound.

## P2 follow-through and limits

- **Cache retirement:** `ProjectIndex.evict` pins every current cache and every publication, while capacity includes all JSON files (`src/context/index.ts:172`, `:197`). No current source retires missing-workspace pointers/publications. The 10 absent selected-cache workspaces are real stale references, but neither cache exhaustion nor an unsafe read was reproduced. Add ownership-aware pointer retirement after positive native cleanup, preserving publications still needed by live readers; test eventual capacity recovery without deleting task history.
- **Recovery activation:** 203,733 trigger-fed facts with zero consumers is a write-producing, currently unconsumed subsystem. Count alone is not a performance defect. Name its intended production consumer and acceptance slice before expanding it. Structured handoff/probe libraries have substantial schemas; native probe walkthroughs and full handoff orchestration are not proven by unit tests or exports.
- **UI workload:** closed trajectory `<details>` still instantiate history/live `<For>` children (`src/trajectory-panel/panel.tsx:1037`, `:1060`, `:1092`, `:1099`). Root observed roughly 811 events in a viewed trajectory and two renderer freezes. Lazy mount/virtualization merits a measured task in the existing trajectory/performance lanes; unsymbolized V8 samples do not establish this as the freeze cause. Existing copy corrections/advice for LZ-169 are already in flight.
- **Schema governance:** main `user_version=7` migrates task storage; RunnerStore and subsystem constructors additionally perform additive schema initialization. That is one database with several schema owners, not 75 independent databases. Establish an inventory/version-compatibility contract for clean install/upgrade and retired tables; do not delete legacy `context_receipts` merely because current source no longer reads it.
- **History/query scaling:** `RunnerStore.plans()` limits all states to 1,000 rows before runtime terminal filtering (`src/runner/store.ts:966`). At 135 project plans this is not an observed outage. A future eligible low-priority plan can fall outside that window. Query active work independently of retained history before that scale; preserve priority. Similarly, measure synchronous Git/SQLite costs before broad service rewrites.
- **Inference settings/lifecycle:** default-location forwarding is the right authority. Each location still registers a unique one-second settings job (`src/webgpu/server.ts:271`), and each Desktop setup polls settings every second (`src/gui.tsx:186`). Shared timer does not coalesce those RPC reads. Measure fan-out before changing notification policy. `ModelLease.lost` uses host lifecycle retirement (`src/webgpu/lease.ts:547`); renderer generation/provider rollover has separate receipt requirements. LZ-159's observed normal reload does not prove navigation-loss races, cross-window recovery or physical GPU backend identity. Keep LZ-165's existing scope and all inference preferences intact.
- **Native verification:** candidate-owned launch isolates process/data/registration identity and preserves retryable cleanup (`src/verification/opencode/owned-launch.ts:372`, `:567`). Its dedicated service port belongs to third-party OpenCode tooling, under the documented exclusion. Project previews still require Portless. Passing fixture tests do not substitute for real Desktop input delivery/readback, original-worker continuation, local inference and release installation/upgrade observations.
