# Integration target, containment, and cleanup audit

Task: `ae06c6e2-043c-43a8-a9f0-961f85545ac9`

## Finding

LAZERS has one integration authority, not separate plan, task, and cleanup proofs: `lz-plan-command` records reviewed integration, and the same change-containment proof is reused by prerequisite dispatch and cleanup. `targetBranch` is a checked-out branch label; the integration proof is evaluated against that checkout's `HEAD`. This supports a non-main target when it is checked out, but does not select an arbitrary branch or identify a PR.

The current receipt is not a landed-range record. It stores the artifact, branch label, observed post-landing `HEAD`, and reason. No target-before head, task-to-commit range, shared PR/group identity, or PR URL/number is stored. Review comparisons remain source-artifact comparisons, not a comparison of actual landed target changes.

No PR merge, PR persistence, branch-switching feature, or parallel integration registry was added here.

## Existing authority and evidence flow

1. `src/runner/tools.ts:43-47` registers `lz-plan-command`; `src/runner/schema.ts:191-276` accepts `integrated` and an optional `targetBranch`. `recordIntegration()` requires the target label, exact accepted artifact, and reason (`src/runner/plan-control.ts:34-74`).
2. `CommandPipeline.preflightProofs()` calls `proofForArtifact()` against the canonical project checkout (`src/runner/command-pipeline.ts:172-209`). `recordIntegration()` then compares the observed current branch with `targetBranch` and requires the proof to contain the exact artifact (`src/runner/plan-control.ts:17-30`).
3. `IntegrationProof.head` is the observed `HEAD`; `proveIntegration()` binds containment to that checkout head (`src/runner/integration-proof.ts:142-174`). The proof tries exact ancestry, change-id notes, patch IDs (including ordered replay and bounded squash search), and tree/merge-tree evidence (`src/runner/integration/containment.ts:61-135,151-275,278-365`). Stored identity supports artifacts whose commit SHA has disappeared (`src/runner/integration-proof.ts:44-78,94-104`).
4. The append-only `runner_transitions` table stores task or plan events. Task integration writes `TASK_INTEGRATION_RECORDED`; plan integration writes `INTEGRATION_RECORDED` and moves the plan into cleanup (`src/runner/plan-control.ts:42-74`; schema at `src/runner/store.ts:958-970`). The event payload contains `{artifact, branch, head, reason}`. Task integration deliberately leaves the accepted plan and workspace available to dependent tasks.
5. Prerequisite consumers require a current event and prove the artifact against the selected checkout baseline. Task dependencies also require the event branch to match the selected branch (`src/runner/prerequisite-proof.ts:83-160,163-238`; store query at `src/runner/store.ts:4505-4530`). Legacy task receipts without `reason` remain accepted; the regression row at `src/runner/prerequisite-proof.test.ts:180-186` exercises that shape. Plan prerequisites validate event ordering/invalidation and current artifact containment rather than treating lifecycle state or recorded head as proof.
6. A limited branch-lineage consumer already exists: `AdoptionPreparation.reviewedAdoptionBaseline()` searches recent integration events for the same branch and selects a recorded head on the candidate's first-parent line that descends from both artifacts (`src/runner/adoption-preparation.ts:147-195`). It establishes an adoption scope baseline, not a general task landing range or PR association.

The selected branch must already be checked out in the canonical checkout. A regression now checks both task integration and whole-plan cleanup on `feature` (`src/runner/runtime-scope.test.ts:200-267`, `src/runner/runtime-cleanup.test.ts:156-186`). This is existing behavior made explicit, not a new target-selection feature.

## Cleanup boundary

`WorktreeCleanup` has independent safety duties after integration has been recorded: it verifies the accepted artifact and owned worktree head against the current checkout, rejects dirty worktrees, confirms worker/check quiescence, rechecks exact native and Git registrations, and records a durable removal effect (`src/runner/worktree-cleanup.ts:253-307,624-711`). It calls `RunnerHost.removeWorktree()` only after those checks. The OpenCode adapter explicitly passes `force: false` (`src/runner/native.ts:775-782`), and `src/runner/native.test.ts:229-243` asserts that contract. Missing, dirty, active, unmerged, or ambiguous work is preserved for reconciliation.

The attempt's `workspace`, `base_commit`, and `artifact` remain in `runner_attempts` after native worktree removal (`src/runner/store.ts:965-970`). Retention retires bulky activity, not attempt records; `src/retention/retention.test.ts:297-301` checks that transitions, effects, and attempts remain. The native location may be retired after removal, so this path is provenance, not a promise that the checkout still exists. Task-level integration does not start whole-plan cleanup, which prevents removal of source still needed by dependencies.

## Review and retention boundary

- Review selects task/attempt artifacts and task-chain bases, or a plan's combined candidate; it does not select an integration receipt's target range (`src/code-review/comparisons/selection.ts:82-116,118-138,140-186`; shared chain rule at `src/runner/task-chain-base.ts:8-30`).
- Historical comparisons store comparison/file metadata and object IDs. `historicalFiles()` reads Git trees/diffs and returns no blobs (`src/code-review/comparisons/resolver.ts:278-302`). Later source reads check `code_review_blobs` then read the Git blob (`src/code-review/comparisons/resolver.ts:202-210,270-275`). The comparison schema and inserts are in `src/code-review/comparisons/store.ts:36-74,150-200`.
- Live capture is stronger: it persists captured blobs, so a previously captured live source remains readable after deleting its worker workspace. `src/code-review/comparisons/comparisons.test.ts:472-609` verifies this and also verifies that a new live capture does not recreate a removed workspace. Historical source reads are not similarly snapshotted; they depend on the Git object remaining available.
- No delete/retention consumer for `code_review_comparisons`, `code_review_files`, or `code_review_blobs` was found under `src/retention` or in the repository's Review store. Comparison metadata therefore accumulates, but persisted metadata alone does not guarantee historical blob availability after the relevant Git objects become unreachable and are pruned.
- `attributionTaskIDs` is file-path attribution in the inventory (`src/code-review/comparisons/inventory.ts:112-139`), not commit ownership or line-level authorship. It cannot be used as evidence that a task landed a specific portion of a batch integration.
