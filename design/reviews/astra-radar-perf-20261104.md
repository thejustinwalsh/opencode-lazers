### Radar: what each agent is doing now

Use a quiet native workbench, compact rows, subtle separators and the existing horizontal inspector split. The defining row connects **agent → assigned task → actual model/effort → current observed activity → target → duration/result**. Show activity from evidence, never infer “editing,” “thinking” or healthy progress from a busy flag.

- **Thin system strip:** connected/partial/stale observation; executing/waiting session counts; scheduler's observed state and most recent decision. Expose pending message delivery/permission or unavailable local inference as actual system signals. Avoid backlog metrics and implementation inventory.
- **Live sessions:** Architect and active worker rows, idle sessions collapsed but discoverable. Each row shows task reference/short title, exact route/effort, native state and current operation. Example layout: `LZ-127 · Luna / Max`, then `read · src/runner/native-idle.ts · 2.4s`. This is illustrative composition, not a claimed live call. Concurrent calls remain separate under their session rather than being forced into one “current tool.”
- **Activity and files:** show calling/running/completed/failed, duration and a short safe result. Explicitly distinguish reading, searching and editing; compact file chips carry the operation verb. A requested edit, successful tool result and confirmed file change are different facts. Where a shell/tool does not expose file attribution, show its known operation and “file activity unavailable.”
- **Trajectory/health:** elapsed current execution and attempt time, recent tool/model phases, last meaningful observed activity age, permission/wait/failure or evidence-backed possible struggle. No percentage complete, inferred inner reasoning or synthetic health score. Unknown coverage must remain visible. A long-running shell can be active without evidence of progress; missing events are not proof of a stall.
- **Live system/message activity:** small timestamped stream of dispatch, model request/result, tool call/result and actual message transfers with source → destination and persisted/admitted/consumed status. Scheduler decisions belong here as events; task prioritization and future work belong in Tasks. Collapse repeats with count/time range, retaining historical access.

**Narrow, 330–450 CSS px:** strip, compact two/three-line session rows, recent flow, then lower inspector. The first screen should reveal active agents, their actual tools/targets and durations. **Wide:** aligned session/task, model/effort, operation/target and duration/result columns above the same lower inspector. Do not expand cards to fill width. Selection is stable across updates; elapsed text advances on a visible-only clock without data fetches. Selecting a session/tool/file/flow event reveals its bounded detail, timing provenance and related history. Provide Open worker, Open task, Open trajectory and file/diff navigation only where the actual target is known. Raw metadata/C4/XState stay behind diagnostics. Preserve focus, scroll, theme/font and reduced-motion behavior.

## Idle model recommendation

Recommend **5 minutes** as the initial finite idle timeout for discussion. It is a practical compromise among existing 1/5/15-minute options, not a benchmark-derived optimum. Measure reload time and energy across ordinary bursts as well as idle savings. Use 1 minute for stronger memory reclamation if ordinary work tolerates reload cost; Never is reasonable when repeated quick use earns retained memory. No setting was changed.

A resident model retains memory and device/session resources, but residency does not itself mean continuous inference. Here there is separate proven 500ms polling. Six enabled features do not imply six simultaneously loaded models: `src/webgpu/lifecycle.ts:23` serializes exclusive model ownership. Runtime unload releases model resources and detaches the broker (`src/webgpu/runtime.ts:461`); decision disposal calls ORT `release()` and WebGPU `destroy()` (`src/webgpu/decision-runtime.ts:88,94`). Official ORT documents release of underlying session resources and distinguishes it from model execution: [InferenceSession](https://onnxruntime.ai/docs/api/js/interfaces/InferenceSession.html). WebGPU specifies device destruction/resource cleanup: [WebGPU device lifecycle](https://www.w3.org/TR/webgpu/#dom-gpudevice-destroy). Neither API promises a particular idle wattage or immediate OS resident-memory drop. Unloading can reclaim capacity; fixing polling addresses avoidable activity. Both should be evaluated separately.
