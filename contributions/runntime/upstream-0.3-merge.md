Auto-merged files reviewed for semantic conflicts (all compile, lint and pass):

- `core/weights/transforms.ts`: the fork's offsets threading through `permuteRows`/`splitRows`/`concatRows`/`scaleWeight`
  sits beside upstream's `sources`. One real bug: upstream's `dequantize` ignores `offsets`, so a Q4_K weight sent through it
  (conv fallback, gpu `Embedding`) would silently lose its offsets. `dequantize` now adds them.
- `core/nn/module.ts`, `core/index.ts`, `zoo/index.ts`, `zoo/models.ts`, `README.md`, `astro.config.mjs`: additive, no key or
  name collisions. Version stays 0.3.0 (upstream's bump; the fork does not touch it).
- `layers.test.ts`, `transforms.test.ts`: the fork's `quantTensor` call needed `sources: []`.
- Upstream's renames against fork state-dict keys: `RMSNorm.scale` is now `weight`. The D1 hook and the LFM3 chat and audio
  hooks renamed checkpoint `.weight` to `.scale`; those renames are deleted (checkpoint names now match), and
  `lfm3/model.ts` reads `.weight`. The GGUF name map in `lfm3/audio/model.ts` targets `.weight`. LFM3 hook test expectations
  updated.
- `derivedTensor` is gone upstream. D1, LFM3, `gguf.ts` and their tests now use `deriveFromTensors` / `derive`; every
  `quantTensor` they build carries `sources` (GGUF: the tensor's own range; D1 and padded LFM3 projections: their inputs'),
  so `loadStateDict` binds them in file order.
- `test/zoo/leaks.gpu.test.ts` (upstream's): MiniLM expected two 20 B id/position uploads to leak. The fork's D1 lifetime work
  (`releaseAfterSubmit` in `gatherRowsSpec`) frees them after submit, so the expectation is now the two 40 B uploads only.
  Upstream passes this test on its own tree; the change is the fork's, positive, and belongs in the PR that carries
  `eval.ts`/`shape.ts` (row 3).

## What upstream made redundant or broke in the fork's code

- Fork's `derivedTensor`: removed upstream; all uses ported.
- Fork's norm-weight renames in D1 and LFM3 hooks: redundant, deleted.
- Fork's duplicated offsets reorder loop in `Linear`: replaced by shared helpers.
- Upstream's `dequantize` and `Embedding` hook would have dropped Q4_K offsets and the cpu quantised table; patched as above.
- Upstream's quantised conv1d (#97) touches the fork only in the conv scale layout; the depthwise kernel is unaffected.

## Concerns left

1. `quantRows` (D1) and `padQuantizedRows` (LFM3) drop `offsets`. Safe today (both only see Q8, symmetric), wrong for a
   Q4_K tensor. Unchanged from the fork; flag before upstream review.
2. Offsets exist only on the default grouped scale layout. A conv or custom `scaleAt` with offsets is unsupported and untested.
3. `Embedding`: a gpu table dequantises a quantised weight, a cpu table keeps it quantised. Reviewers may ask for one behaviour.
4. Open upstream PRs #131, #124, #127, #130 touch the same quantisation and load paths; another merge is likely.
5. UPSTREAM-READINESS.md blockers 1 and 4 (commit identity, unfinished ledger stages) are unchanged: the fork history is not
   submittable as is; the series is new commits from `upstream/main`.
6. GPU results are one machine, one browser.
